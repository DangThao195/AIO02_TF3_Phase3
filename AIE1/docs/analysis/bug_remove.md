# Proposal: Remove Candidate Q/A Wrapper Responses

## Problem

The Ask AI UI sometimes displays responses in this format:

```text
AI Response: **Question:** How many reviews are there for the Eclipsmart Travel Refractor Telescope? **Answer:** There are 5 reviews. (trusted_review_facts.review_count)
```

This is incorrect UX for the product-review assistant. The user did not ask the model to generate a new question-and-answer pair. The assistant should answer the user's original question directly, or return the standard out-of-scope/no-info response.

Important scope note: this bug is not limited to unrelated or off-topic inputs. It can also happen when the original user question is genuinely product-related. The core problem is that the candidate response violates the output contract by wrapping the answer in a generated `Question:` / `Answer:` template.

## Current Behavior

Current runtime behavior:

1. The frontend sends the raw user question to `AskProductAIAssistant`.
2. The backend performs input safety filtering and a narrow off-topic routing check.
3. If the question is not caught by `is_clearly_off_topic_question()`, the Bedrock path fetches product reviews and product info.
4. The candidate model receives the original question plus grounded product/review context.
5. The candidate sometimes wraps the answer in its own `Question:` / `Answer:` format.
6. `post_process_output()` does not reject this wrapper format.
7. The fidelity judge may approve the answer because the factual claim is grounded.
8. Approved responses may be cached and later returned repeatedly.

## Root Cause

The `Question:` / `Answer:` wrapper is not generated by the frontend and is not explicitly formatted by backend code.

The wrapper is generated by the candidate LLM. In some cases this happens when the model tries to "repair" an ambiguous or out-of-scope user input into a product-related question. In other cases, the original user question may already be product-related, but the model still chooses a Q/A answer style because the prompt asks it to answer from structured evidence and the runtime does not enforce a strict final-answer format.

The runtime currently lacks a hard output contract that forbids this format. That is the main issue.

Relevant source locations:

- `ProductReviews.tsx` only renders the backend response string and does not add `Question:` / `Answer:`.
- `product_reviews_server.py::build_system_prompt()` instructs the model not to repeat or restate the user's question.
- `product_reviews_server.py::build_bedrock_user_prompt()` also instructs the model not to repeat or restate the user's question.
- `product_reviews_server.py::post_process_output()` does not currently reject `Question:` / `Answer:` wrappers.
- `guardrails/evaluator.py` primarily checks factual grounding. It may approve a response if the factual claim is supported, even when the answer format or intent alignment is wrong.
- `guardrails/cache.py::should_cache()` does not currently reject approved responses that contain a Q/A wrapper.

## Why Prompt-Only Fix Is Not Enough

The system prompt already tells the model:

```text
Do not repeat or restate the user's question in the answer.
```

However, this is a soft instruction. Once the model sees product/review context, it can still produce a grounded but incorrectly formatted answer. Prompting reduces the chance of this bug, but it does not enforce the output contract.

The fix should therefore be implemented as runtime validation, not only prompt tuning.

## Proposed Solution

Use a small, deterministic output-format gate after candidate generation and before judge/cache. This gate must run for every candidate response, including product-related questions.

### 1. Add Output Wrapper Detection

Add a helper such as:

```python
def has_question_answer_wrapper(text: str) -> bool:
    normalized = text.strip().lower()
    return bool(
        re.search(r"(^|\n|\*\*)\s*question\s*:", normalized)
        and re.search(r"(^|\n|\*\*)\s*answer\s*:", normalized)
    )
```

This gate should detect common variants:

- `Question: ... Answer: ...`
- `**Question:** ... **Answer:** ...`
- `Q: ... A: ...`

### 2. Reject Wrapper in `post_process_output()`

Update `post_process_output()` so candidate responses with Q/A wrapper are not shown to the user.

Recommended behavior:

```python
if has_question_answer_wrapper(filtered_result):
    return UNVERIFIED_SUMMARY_MESSAGE
```

The output-format gate should not try to infer the correct final answer. Its job is only to prevent malformed model output from reaching the user or cache. Returning the existing unverified/fallback message is safer than turning a malformed product-related answer into `NO_INFO`, because `NO_INFO` means "the evidence is missing", while this bug is a formatting/intent-control failure.

If the original question is already known to be clearly out of scope before candidate generation, the pre-routing gate should return `OUT_OF_SCOPE_MESSAGE` earlier. Once candidate output exists, a Q/A wrapper should be treated as malformed candidate output.

### 3. Do Not Cache Wrapper Responses

Update `should_cache()` to reject Q/A wrapper responses even if judge approved them:

```python
if has_question_answer_wrapper(response_text):
    return False
```

This prevents a bad approved response from being replayed for 24 hours.

### 4. Strengthen Judge Rubric For Intent Alignment

The judge should not only evaluate factual grounding. It should also reject answers that replace the user's original question with a new question or answer in a generated Q/A template.

Add a rule:

```text
If the candidate answer invents, rewrites, or substitutes a different question, or wraps the final answer in a Question/Answer template, mark the answer unsupported even if the factual claims are grounded.
```

This handles cases where the answer is factually correct but violates the expected assistant response format or does not answer the user's actual request.

### 5. Add Regression Tests

Add focused tests for:

- `**Question:** ... **Answer:** ...` is rejected.
- `Question: ... Answer: ...` is rejected.
- Product-related questions that receive a Q/A wrapper are rejected as malformed output.
- Normal direct answers still pass.
- Out-of-scope personal statements such as `toi ten la Thinh` do not enter the RAG path.
- Q/A wrapper responses are not cached.

## Recommended Pipeline After Fix

```text
User question
-> input safety filter
-> off-topic / scope gate
-> fetch reviews/product info only if product-review scope is valid
-> candidate LLM
-> output format gate
-> runtime judge: grounding + intent alignment
-> cache only if approved and format-valid
-> UI response
```

## Expected Result

Bad output:

```text
**Question:** How many reviews are there for the Eclipsmart Travel Refractor Telescope? **Answer:** There are 5 reviews.
```

Should no longer reach the UI.

Instead, depending on the original user question:

- If the original question is unrelated to product reviews: return `This question is out of scope. I only answer questions related to the product.`
- If the original question is product-related but lacks evidence: return `No information in reviews.`
- If the original question is product-related and the model returns a Q/A wrapper: block the malformed output and do not cache it.
- If the original question is valid and supported: return a direct natural-language answer without a generated Q/A wrapper.

## Tradeoffs

This approach is intentionally small and deterministic.

Advantages:

- Does not require adding another LLM call.
- Does not rely only on prompt compliance.
- Prevents malformed responses from reaching the UI.
- Prevents bad approved responses from entering cache.
- Keeps the existing RAG and judge architecture intact.

Limitations:

- A pure regex gate catches format violations, not all possible intent drift.
- Returning a fallback/unverified message for malformed output may hide an otherwise factual answer, but this is preferable to exposing an inconsistent assistant format.
- A deeper intent classifier could be added later, but it increases latency and flow complexity.
- The judge prompt still needs calibration so factual but off-intent answers do not pass.

## Recommendation

Implement the deterministic output-format gate first. It is the lowest-risk fix for the visible bug.

Then add judge intent-alignment rules and cache rejection for malformed responses. This combination addresses both the immediate UI issue and the longer-term risk of caching factually grounded but off-intent answers.
